My secret scanner was leaking the secret it was supposed to catch.

I found it on my personal OCI Kubernetes GitOps project, while testing a custom Gitleaks rule. The rule blocked the commit, which is what I wanted. Then I read the output, and the "redacted" secret was almost fully visible.

---

## The Setup

The project keeps OCI identifiers out of Git. Gitleaks runs as a pre-commit hook, so a commit that contains a secret is blocked before it leaves my machine.

Gitleaks' default rules don't know OCI identifiers, so `.gitleaks.toml` extends the defaults with three custom rules:

```toml
[extend]
useDefault = true

[[rules]]
id = "oci-ocid"
regex = '''ocid1\.[a-z0-9]+\.oc[0-9]+\.[a-z0-9-]*\.[a-z0-9]{20,}'''

[[rules]]
id = "oci-object-storage-namespace-url"
regex = '''objectstorage\.[a-z0-9-]+\.oraclecloud\.com/n/[a-z0-9]+'''

[[rules]]
id = "oci-api-key-fingerprint"
regex = '''fingerprint\s*=\s*"?((?:[0-9a-f]{2}:){15}[0-9a-f]{2})'''
```

An OCID, an Object Storage namespace URL (it reveals the tenancy namespace), and an API key fingerprint. That last regex is the fixed version. I'll get to what it looked like before.

---

## The Test

I tested with fake values. I staged a temp file containing a fake fingerprint, then ran `pre-commit run gitleaks`. All three rules blocked the commit.

Passing is not the same as working, so I read the finding Gitleaks printed.

---

## Problem 1: 15 of 16 Bytes in the Clear

The fingerprint rule printed 15 of the 16 bytes of the value it had just caught. The entropy score on the finding read about 0.9, which is far too low for something that looks like a key.

The cause was the capture group. Gitleaks redacts whatever the capture group matches. My first version repeated the group, like `([0-9a-f]{2}:){15}`. A repeated group only holds its last repeat, so Gitleaks treated just the final `xx:` pair as the secret and left the other 15 bytes on screen.

The fix was to wrap the whole fingerprint in one group. After that, the finding showed the whole value as `REDACTED`, and the entropy read 3.6.

A scanner that prints what it found into terminal scrollback, CI logs, or a pasted issue is a leak with extra steps.

---

## Problem 2: pre-commit Tests What's Staged

My fix looked right in the editor, but I couldn't tell whether it worked.

`pre-commit` checks what's staged, not what's in your editor. Until I staged the file, my fix wasn't tested at all. The same goes for the config itself: I had to stage the new `.gitleaks.toml` together with a temp file holding the fake fingerprint.

I unstaged and deleted the temp file afterwards. It was never committed.

The same fix went to the app and GitOps repos too, as separate PRs.

---

## What a Commit Hook Doesn't Do

A pre-commit hook is only the first layer. Anyone can skip it with `git commit --no-verify`.

When I posted this, running the same Gitleaks config in CI was the next step. It's done now: a CI job scans the full history in all three repos, because that's the layer `--no-verify` can't bypass.

---

## What I'd Do Differently

Test a new rule by reading its output, not just its exit code. A rule that blocks is only half the job. The other half is what it shows while blocking. Next time I add a rule, "what does the finding print?" gets its own check.
